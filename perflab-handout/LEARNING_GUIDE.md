# Performance Lab · 用证据优化代码

[总路线](../README.md) · [工具箱](../learning/TOOLBOX.md) · 原始依据：[README](README)、[perflab.pdf](perflab.pdf)、`kernels.c`、`driver.c`。

目标是优化 `rotate` 和 `smooth`，保留输出语义和原测试。当前函数仍使用起始基线；指南不替你写优化实现。

## 热身：把数学变成下标

给 3×3 图像的每个像素写不同编号，手画旋转后的图像；挑一个角、一个边、一个中心像素，手算平滑所需邻域和样本数量。旋转方向以当前 `naive_rotate` 为准，不凭想象确定。

过关标准：能用源坐标、目标坐标说明映射；知道平滑的角、边、内部邻居数量不同。邻域累加后再取整数平均，提前逐项除法可能改变结果。

## 关键知识

| 概念 / Concept | 练习中的证据 |
|---|---|
| 空间局部性 / Spatial locality | 连续访问的地址与访问步长 |
| 循环开销 / Loop overhead | 分支、索引计算与每像素工作的比例 |
| 公共计算 / Common computation | 内层反复执行却不随内层索引变化的表达式 |
| 边界处理 / Boundary handling | 安全与内部快速路径如何兼顾 |
| 测量波动 / Measurement variation | 相同程序多次运行的周期差异 |

## 阶段 1：先建立可信基线

```sh
make
./driver
```

需要 32 位编译环境。按源码要求填写自己的 team 信息；这是你开始实验的操作，指南没有代填。读取每个尺寸的正确性、CPE 与加速比，保存至少三次测量的范围。

过关标准：能解释“相对哪个基线加速”，知道一次最快结果不能代表稳定收益。保持计时环境尽量一致。

## 阶段 2：rotate，一次研究一个因素

先探索减少索引计算，再研究访问顺序和分块。写出每次改动的预测，例如“改善目标写入连续性可能减少某类访存代价”，然后用结果核对。

原框架支持注册多个候选版本，你在解题时可按 `register_rotate_functions` 的接口保留版本进行比较；最终评分入口仍是 `rotate`。所有候选必须通过正确性检查。

过关标准：各测试尺寸都正确，收益超过测量波动；能解释变快的原因和在哪种尺寸可能变慢。没有稳定收益的版本应记录为实验结果，不算成功优化。

<summary>提示 1：分块后角落错了</summary>

检查块边界与图像边界是否独立处理，旋转下标是否使用了正确的全局坐标。用带唯一编号的小图定位第一次写错的像素。

</details>

## 阶段 3：smooth，隔离边界复杂度

先确认逐通道求和的类型足够宽，避免中间值溢出。再区分角、边、内部的工作，探索复用邻域信息或减少重复计算。每个变体都按完整输出检查，不能只比较总和。

过关标准：边界像素和内部像素都正确，所有原尺寸通过；知道优化后的整数舍入是否与基线一致。

<details>
<summary>提示 2：图像看起来一样，测试仍失败</summary>

“肉眼相近”不是逐像素相同。记录一个错误像素的每个通道、参与邻居、总和、除数与除法顺序，检查是否多读了邻居或改变了截断时机。

</details>

<details>
<summary>提示 3：代码更短，为什么更慢</summary>

源代码长度不代表机器工作量。比较内层访存次数、地址计算、分支、函数调用和工作集，找一个能解释具体尺寸结果的假设。必要时对自己的候选查看汇编。

</details>

## 完整验收与进阶

```sh
make
./driver
./driver -g
```

`-g` 按本地驱动检查正式入口 `rotate` 和 `smooth`。最终入口必须采用你验证过的版本，不能仅注册了更快候选而未更新入口。保留原评分规则，以原讲义要求验收性能。

进阶：为两种访问顺序画地址轨迹；用多次测量展示“优化收益”和“波动”区别；把一种优化迁移到矩形或非整块规模的独立练习。不要修改官方驱动来迎合自己的实现。
